# Decision Framework — Escaping the Build Trap Pack

## Diagnosing which layer the build trap lives in

| Symptom | Likely layer |
|---------|-------------|
| Team backlog is feature-driven, no discovery | Team-level (fix: adopt product kata locally) |
| Team wants outcomes, but roadmap from above is a committed feature list | Portfolio/strategy layer (fix: push back on the cascade, request outcome-based direction) |
| Leadership reviews only celebrate ship counts | Executive reporting layer (fix: propose outcome metrics for business reviews) |
| PM job descriptions/hiring emphasize delivery coordination only | Org-design layer (fix: redefine the PM role's mandate) |

Fixing the wrong layer (e.g., asking one team to "just do discovery" while executive incentives still reward ship velocity) produces friction without lasting change — diagnose the highest layer showing the symptom.

## Applying the product kata at any layer

1. State the direction from above (vision/strategic intent) — if none exists, that's the fix needed first.
2. Grasp the current condition with real data (not opinion) for the metric this layer owns.
3. Set a target condition: a specific, time-bound outcome to reach — not a feature.
4. Run iterations (build-measure-learn) toward it, treating obstacles discovered along the way as the next thing to solve, not a discovery-process failure.

## Escaping incrementally vs. all at once

Org-wide build-trap escape (BT1-BT7 org-wide) is a multi-quarter change effort, not a memo. Prioritize: (1) get one team practicing full outcome-driven discovery as a proof point, (2) shift one layer of executive reporting to include outcome metrics, (3) rewrite roadmap format for the next planning cycle. Don't wait for full organizational buy-in before starting locally.
