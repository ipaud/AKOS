# Philosophy — Tool Design

## The tool definition is the agent's entire world

When a person picks up an unfamiliar API they are not really working from its signature. They have the docs open, a search engine, a colleague two desks away, a memory of the last three APIs shaped like this one, and — decisively — the option to make a throwaway call and read what comes back. An agent choosing a tool has the name, the description, the schema, and nothing else. Every one of those human affordances is absent, and the gap does not disappear; it gets paid for in wrong calls. This is why tool design is not documentation work that follows the real engineering. For the agent, the definition *is* the tool. A capability with a perfect implementation and an ambiguous name is, in the only sense that matters here, an ambiguous capability.

## Ambiguity is the cost center

The characteristic failure of an agent-facing tool is not an outage. It is a run that takes eleven calls where four would have done: one to guess at a parameter format, one to read the error, one to try the other tool that also sounded right, one to discover a prerequisite nobody mentioned. Each of those calls costs latency, tokens, and a slice of the context window, and each leaves residue in the transcript that makes the next decision slightly worse. The economics are unintuitive because every individual call succeeds or fails cheaply — the cost is distributed across the whole run and shows up as "the agent is a bit unreliable on this task," which reads like a model problem and is an interface problem. Removing one ambiguity from a description is often worth more than any prompt engineering applied downstream of it.

## "OK" is a lie of omission

A tool that answers a write with a success token is asking the agent to take its word for it. The agent has no way to distinguish "the operation did exactly what you meant" from "the operation did something, and it did not throw" — and the second is where the interesting failures live, because the arguments were valid and the effect was not the one intended. What happens next is predictable: the agent reports success, because it has nothing else to report, and a claim enters the transcript that nobody verified and that later turns will treat as established. A response carrying the resulting state closes that loop inside a single call. The agent can compare what it wanted to what it got, catch its own mistake in the turn it made it, and — when it does report success — be reporting something it actually checked.

## Blast radius belongs at the boundary that knows it

Between what an agent intends and what its arguments actually select there is a gap that neither side can see. The agent's filter matches four records in its mental model of the data; the database has four thousand. Nothing about the call distinguishes the two cases, and the difference only becomes observable after the operation has already happened. The tool, on the other hand, knows. It can count before it commits, and it can hand that count back before doing anything irreversible. This is why previews and confirmations are not a courtesy layered over a capability but a property of a capability that is safe for an agent to hold — the same argument for why an unbounded result set is a defect in the tool rather than an oversight by the caller. The participant that can measure the consequence is the one responsible for bounding it.

## Composition survives partial failure; monoliths do not

The pull toward one tool that handles the whole operation is strong, because from the outside it looks like the agent's job just got easier — one call instead of four. What it actually does is destroy the agent's ability to recover. When four effects hide behind one name and the third fails, the agent receives a single error and no way to learn what landed. Retrying re-applies the first two; not retrying leaves the fourth undone. Both are wrong, and there is no information available with which to choose between them. Small tools keep the failure where it happened and keep the state observable at each step, which is what makes recovery a decision rather than a gamble. The convenience of the monolith is real and it is borrowed against the first bad run.

## Your first draft is written from the wrong side

A tool description is written by the person who built the tool, in the state of knowing exactly what it does — which is precisely the state in which its ambiguities are invisible. You cannot introspect your way to a good description, because the thing you would need to notice is the thing your knowledge conceals. The only reliable source of signal is watching an agent actually use it: the parameter it fills with the wrong kind of value, the neighbouring tool it reaches for instead, the sequence it invents because nothing indicated a prerequisite. That evidence is cheap, and it is the difference between a description that reads well to its author and one that works. Treating the first version as a draft to be corrected against observed behavior, rather than a specification to be defended, is most of the discipline.

## Where this philosophy stops

This pack is about the shape of a tool an agent calls. It does not cover the security controls guarding that tool — injection arriving through tool output, a tool description written to manipulate the agent reading it, permissions broader than the task needs, consent and audit — which belong to [agent-security](../agent-security/README.md), including MCP's trust-boundary and authorization concerns. It does not decide whether the calling system should have been an agent at all, or how its loop terminates and recovers; that is [agent-foundations](../agent-foundations/README.md). And it does not govern what happens to a tool's output once it lands in the window, which is [context-engineering](../context-engineering/README.md) — though the two meet directly at the unbounded result set, where a tool-design defect becomes a context-engineering failure one call later. Nothing here licenses skipping the safety floor: a tool satisfying every rule in this pack can still be one an agent should not have been given.
