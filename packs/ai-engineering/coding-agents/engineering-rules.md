# Engineering Rules — Coding Agents Pack

Checkable in a diff, a commit history, a pull request, a session transcript, or a CI log. A reviewer verifies each against the actual artifact; violations are findings.

## Repository orientation

- CAE1. Before the first write, the project's build, test, lint, and type-check entry points are identified from the repository itself (package manifest, Makefile, CI config, contributor docs) rather than assumed from the language.
- CAE2. The files the change will touch are located by search or by an index before any of them is opened for editing, not discovered one at a time while editing.
- CAE3. The project's stated contributor conventions (a `CONTRIBUTING` file, a style config, an agent-instructions file at the repository root) are read before the first edit when they exist.
- CAE4. The change's target directory is inspected for local conventions — file naming, test placement, import ordering, error handling — before a new file is added to it.
- CAE5. Where a project pins a dependency version, the installed version is what conventions and APIs are checked against, not the latest published version.
- CAE6. The working tree's starting state is known before editing: whether it is clean, which branch is checked out, and whether uncommitted changes from another source are present.
- CAE7. An orientation phase ends with a stated plan naming the files to change; discovering a materially different structure mid-edit triggers a restated plan rather than silent improvisation.

## Search before edit

- CAE8. Any identifier being renamed, removed, or changed in signature is searched for repository-wide before the first edit, and the search result set is enumerated.
- CAE9. The search covers non-code references: tests, fixtures, documentation, configuration files, serialized data, and string literals naming the symbol dynamically.
- CAE10. Re-exports, aliases, and barrel/index files are followed, so a symbol reachable under a second name is included in the enumerated set.
- CAE11. The change is complete only when every enumerated reference is handled; a reference deliberately left unchanged carries a stated reason.
- CAE12. A search that returns an unexpectedly small result set is re-run with a broader pattern before being trusted — a zero-hit or one-hit search on a symbol expected to be widely used is treated as a possible search error, not as evidence.
- CAE13. Where the language provides a symbol-aware lookup (a language server, a compiler-driven rename, a type checker), it is preferred over plain text search for finding call sites.

## Read before write

- CAE14. No file is written whose current contents were not read in the current session.
- CAE15. A targeted edit against known existing text is preferred over a whole-file rewrite whenever the change affects part of a file.
- CAE16. A whole-file rewrite of an existing file states why a targeted edit was insufficient.
- CAE17. Generated files, lockfiles, and vendored directories are regenerated by their generator rather than hand-edited.
- CAE18. Where a file was read early in a long session and is being written much later, its current contents are re-read before the write if anything could have changed it in between.

## Matching existing conventions

- CAE19. New code matches the surrounding file's naming scheme, indentation, quoting, import ordering, and formatting, as observed rather than as configured in the abstract.
- CAE20. Error handling in new code uses the pattern already in use in that module (exceptions, result types, error returns, a shared error helper) rather than introducing a second pattern alongside it.
- CAE21. New tests are placed where the project already places tests, named the way the project already names them, and use the assertion library already in use.
- CAE22. No new dependency is added when an existing dependency or the standard library already covers the need; adding one carries a stated justification.
- CAE23. No formatting-only changes are made to lines the change does not otherwise touch, and no reformat of an untouched file is included.
- CAE24. A convention the agent would argue against is still followed within the change; a proposed convention change is raised separately and not implemented as part of unrelated work.
- CAE25. Where the project's formatter or linter has a configuration, it is run rather than its rules being reproduced by hand.

## Patch scope

- CAE26. The diff contains only changes required by the stated problem; no unrelated rename, cleanup, dead-code removal, or comment update is bundled in.
- CAE27. Improvements noticed during the task are recorded (an issue, a note, a follow-up list) rather than added to the current diff.
- CAE28. Where a fix genuinely requires a refactor, the refactor is a separate, behavior-preserving change landed before or after the fix, not interleaved with it.
- CAE29. Mechanical changes (renames, file moves, formatting) are separated from semantic changes, so each can be reviewed at the appropriate depth.
- CAE30. No debugging artifacts remain in the diff: temporary logging, commented-out experiments, scratch files, or a loosened check left over from investigation.
- CAE31. No behavior outside the stated problem is changed silently; a behavior change discovered to be necessary is stated explicitly in the change's description.
- CAE32. The diff introduces no new abstraction — a wrapper, an interface, a config option — that has exactly one caller and no stated second one.

## Verifying the API exists

- CAE33. Every external function, method, flag, config key, environment variable, or schema field used for the first time is confirmed against the installed version's source, type definitions, or `--help` output before the call is written.
- CAE34. A confirmation is a lookup in the artifact, not a recollection: "this library has a `retry` option" is checked in the dependency, not asserted from familiarity.
- CAE35. Where a symbol cannot be confirmed, the code is not written against it; the gap is reported instead of filled with the most plausible name.
- CAE36. Package names are verified to exist in the registry before being added to a manifest, and the resolved version is the one recorded.
- CAE37. CLI invocations constructed by the agent are validated against the installed tool's actual interface, not against a remembered flag set from a different version.

## Reproduce and test

- CAE38. A bug fix begins with a reproduction that fails, and the failure's exact output is recorded before any code changes.
- CAE39. After the fix, the identical reproduction is re-run and its passing output recorded; the before and after are both from actual executions.
- CAE40. The reproduction is captured as a regression test wherever the project has a place for one, so the fix is defended against reintroduction.
- CAE41. Every new or modified test is deliberately made to fail once — by breaking the code under test or its fixture — and the failure observed before the test's passing result is trusted.
- CAE42. A test asserting an absence (nothing is detected, no error is raised, a list is empty) is paired with a positive case proving the mechanism under test can produce a result at all.
- CAE43. The full relevant test suite is run after the change, not only the individual test written for it.
- CAE44. Where a test fails after a change, the failure is diagnosed to determine whether the code or the test is wrong; the test is amended only when it is demonstrably the incorrect party, and the reasoning is stated.
- CAE45. A test skipped, quarantined, or marked expected-to-fail as part of the change carries a stated reason and a stated condition for re-enabling it.

## Build, lint, and type verification

- CAE46. The project's build runs to completion after the change, and its exit code is checked.
- CAE47. The project's type checker runs after the change, and new type errors are treated as failures of the change.
- CAE48. The project's linter and formatter run after the change; new violations are fixed rather than left for CI to surface.
- CAE49. A check that cannot be run in the current environment is named explicitly as unverified in the change's report, rather than omitted from it.
- CAE50. Verification runs the project's own command as defined in its manifest or CI config, not a hand-constructed equivalent that may differ in flags, scope, or configuration.
- CAE51. Verification is run after the final edit, not after an intermediate one; an edit made subsequent to the last verification invalidates it.

## Executed evidence

- CAE52. Every completion claim asserting a verifiable state names the command that produced it, and that command was actually executed in this session.
- CAE53. The exit code of every verification command is observed, and a nonzero exit is treated as failure regardless of how the output text reads.
- CAE54. A verification command is not piped into another command that would mask its exit status; where a pipeline is unavoidable, the failure is propagated explicitly (a pipefail setting, `PIPESTATUS`, or capturing the status before the pipe).
- CAE55. Output is not truncated in a way that hides the failure summary; where truncation is necessary, the exit code is captured separately and reported.
- CAE56. A command whose output is empty is not read as success; the exit code decides, and an unexpectedly empty result is investigated as a possible invocation error.
- CAE57. A verification run against a stale artifact (a cached build, a previous test run's output, a pre-edit log) is not counted; verification postdates the change it verifies.
- CAE58. Where a tool is expected to fail and does not, the absence of failure is investigated rather than accepted — a suite that passes when the code is deliberately broken has proven the suite is not running.
- CAE59. The report distinguishes what was executed from what was inferred; any aspect of the change not covered by an executed check is named as unverified at the point a reader would assume coverage.

## Interface change and migration

- CAE60. Before a shared interface changes, its consumers are enumerated, including consumers outside the repository where they exist.
- CAE61. Where all consumers are in-repo, the definition change and every caller update land together, so no commit leaves the tree in a non-building state.
- CAE62. Where consumers are outside the repository or cannot be updated in the same change, the new form is added alongside the old, the old is marked deprecated with a stated removal condition, and removal is a separate later change.
- CAE63. A database migration ships with its reverse, or with a stated, recorded reason why the change is irreversible.
- CAE64. A destructive migration step (dropping a column, table, or index) is separated from the code change that stops using it, and lands after the code change is deployed and stable.
- CAE65. A change to a serialized format, a wire protocol, or a persisted schema states its compatibility direction: whether old readers can read new data, new readers can read old data, or both.
- CAE66. A configuration key that is renamed or removed keeps the old key working with a deprecation warning for at least one release, unless the project has a stated policy permitting otherwise.

## Commits and diff reviewability

- CAE67. Each commit contains one coherent change and leaves the repository in a state where the build and tests pass.
- CAE68. A commit that could not be reverted alone without breaking the tree or removing unrelated work is split before it lands.
- CAE69. Commit messages state what changed and why, in the project's existing format; a message describing effort ("various fixes", "updates") rather than change is rewritten.
- CAE70. A large change is split into a sequence of commits each independently reviewable, rather than landed as one commit whose size prevents review.
- CAE71. Generated or mechanically-transformed output (formatter passes, codegen, lockfile updates) is committed separately from hand-written changes.
- CAE72. Nothing is committed that was not intended to be: no scratch files, no local configuration, no credentials, no editor artifacts. The staged set is inspected before committing.

## Pull request description and review response

- CAE73. The description states what changed, why this approach was chosen, and what alternatives were considered and rejected where a real choice existed.
- CAE74. The test plan lists the exact commands run and their real results, not a description of what testing would cover.
- CAE75. Known gaps — untested paths, unverified checks, deferred work, ordering caveats — are stated in the description rather than omitted because they weaken it.
- CAE76. The description does not claim a verification that was not performed; a claim without a corresponding executed command is removed.
- CAE77. A failing CI check is addressed by fixing its cause; disabling the check, excluding the file, loosening the rule, or retrying until it passes is not a resolution.
- CAE78. A suppression added for a demonstrated false positive is narrow (a single line or symbol, not a file or a rule), in place, and carries a comment explaining why the check is wrong here.
- CAE79. A review comment is resolved by changing the code or by an explicit, stated disagreement; it is not closed by a reply that restates the original reasoning without addressing the objection.
- CAE80. After responding to review or CI feedback, the verification commands are re-run — a change made after the last green run has not been verified.
