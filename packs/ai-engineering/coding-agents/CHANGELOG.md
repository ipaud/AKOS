## [1.0.0] — 2026-07-20

### Added

- First complete version: all 17 schema files populated with operational content. Authority level 2, review cadence 365 days (`review_after: 2027-07-20`).
- Principles CA1–CA18, each with an operational corollary, organized as a spine plus four phases. The spine: plausible is not correct, an unchecked success claim is a defect rather than a shortcut, and a check that cannot fail proves nothing. Before the edit: map the repository first, search before editing because the first match is not the set, read before writing, and never call an API you have not verified exists. The edit: existing conventions outrank better ones you know, smallest correct diff, a shared-interface change is a migration not an edit, and reproduce a failure before fixing it. After the edit: the exit code is the verdict, build/lint/type checks are part of the change, fix the cause rather than suppressing the check, and confidence is bounded by what was executed. The record: a diff is written to be read, a commit is a revertable unit, and a PR description is a claim under review.
- Engineering rules CAE1–CAE80, grouped into repository orientation, search before edit, read before write, matching existing conventions, patch scope, verifying the API exists, reproduce and test, build/lint/type verification, executed evidence, interface change and migration, commits and diff reviewability, and PR description and review response.
- The evidence ladder as the pack's central decision instrument (`mental-models.md`, `decision-framework.md`): described → written → parsed → executed → asserted-against-a-known-failure, with only the top two rungs counting as evidence and every rung below being a prediction wearing the grammar of a result.
- The exit-code chain model and its named trap: a pipeline reports its last stage's status, so `cmd | tail` reports `tail`, which succeeds essentially always — including when the check it is displaying failed catastrophically. Stated as an engineering rule (CAE54), a critical checklist item, a scored CRITICAL finding, and a worked example, because this repository hit exactly this trap during the v1.4.0 work (commit `748db87`).
- Anti-patterns derived from the pack's own principles: the plausible completion, the vacuous pass, the pipe-swallowed exit code, the first-match fix, the blind overwrite, the invented API, the imported style, the bundled refactor, the unreproduced fix, the suppressed check, the silent interface break, the sprawling commit, the marketing description, the stale green, and the confident unknown.
- Review checklist and scoring rubric that treat a **false record** — a completion claim, green check, or description misrepresenting what was verified — as a correctness defect rather than a process concern, with a hard cap at 59 for any open CRITICAL, a cap at 39 when no verification command was executed at all, a cap at 69 when commands ran but exit codes were never observed, and a cap at 79 for a bug fix with no observed red state. No credit for instance-only fixes where a check could have prevented the class.
- A real, inspectable in-repo case study in `examples.md`, drawn from this repository's v1.4.0 quality-infrastructure initiative (thirteen commits; see `CHANGELOG.md`'s `[1.4.0]` entry). Named bugs, each caught only because a command was executed and its actual exit code read: the BSD `awk` `write_marked_section` failure whose prior idempotency check had passed by coincidence; the suppression window that checked only the exact evidence line; `A11Y_INPUT_NO_LABEL` recognizing HTML's `for` but never JSX's `htmlFor`; the fixture-path exclusion matching `"test"` as a substring rather than a path segment; the anon-role JWT wrongly flagged as a secret; the inverted `freshness --fail-on` severity comparison, caught by a run that exited 2 where it should have exited 0; the benchmark harness resolving fixture paths against the wrong base directory, whose failure pattern — every true positive failing while every true negative vacuously passed — is the clearest instance of a check that could not fail; and the piped-`tail` exit-code trap. Each entry states what would have shipped broken had the agent claimed success without executing.
- Positive discipline recorded from the same range, not only failures: deliberately disabling a detector to confirm the benchmark suite could actually fail before trusting that it passed (`b9e0b93`); tracing a failing test to the test itself rather than relaxing its assertion (`4925d34`); reformatting four outlier packs to the convention forty-four others already used rather than growing the parser; and a commit message stating honestly that its CI workflow referenced test directories not landing until the next commit.
- The practice of leaving the project verifiable after each step is attributed explicitly to **this repository's own observed working discipline**, cited to real commits, and is *not* attributed to any external paper. The broader question it opens — how an agent maintains that property across a long-running multi-session effort — is recorded as deliberately deferred to a future `long-running-agents` pack.
- Source cited: SWE-agent (Yang et al., arXiv), for the idea that the interface an agent acts through shapes its error rate and that cheap feedback placed at the moment of the edit prevents defects expensive to catch later — restated operationally as CA13. The pack is organized around the AKOS 17-file contract rather than the source's structure, and no other external source is claimed.
- A pre-edit orientation worksheet, a completion-claim audit, and a verification trace as injectable prompt fragments, alongside the standard build-mode constraint block, review lens, and tight-budget one-liner. The review lens requires the transcript, on the stated ground that a completion claim cannot be reviewed against the summary that makes it.
- Scope boundary recorded against `packs/ai-engineering/agent-foundations` (system shape and bounding, which explicitly deferred repository-editing discipline to this pack), `packs/ai-engineering/context-engineering` (what the agent can see), `packs/architecture/*` (whether the design is good), and `packs/testing/*` (what the test strategy should be).
- Cross-links recorded to `core/authority-model.md` (the Level 2 assignment), `core/confidence-model.md` (the classes behind CA15's evidence-bounded confidence), `core/source-policy.md` (this pack's own distillation discipline), and `core/scoring-model.md` (scoring bands); and to the `testing/tdd`, `devops/git`, and `architecture/martin-fowler-refactoring` packs — TDD as the older home of the red-before-green discipline CA3 and CA11 restate in agent-shaped form, git for commit granularity behind the revert test, and refactoring for why a refactor lands separately from the fix that motivated it.
