# Engineering Rules — Privacy Pack

Checkable in the artifact. A reviewer verifies each mechanically; a violation is a
finding. `★` marks floor rules that hold in every reasoning profile — including
Prototype, the moment the prototype touches one real person's data. Parenthetical codes
cite the principle in [principles.md](principles.md).

## Inventory and purpose

- PR1 ★. Every column, event property, and log field holding personal data is recorded in
  a data inventory with its purpose, lawful basis, retention period, and destination
  systems. A field absent from the inventory is a finding. (P2)
- PR2 ★. New personal-data fields are justified at review time: what decision needs it,
  and what breaks without it. "We might want it later" is a rejection. (P3)
- PR3. The inventory covers indirect identifiers — IP address, device and advertising
  identifiers, session and analytics identifiers, free-text fields users paste into. (P1)
- PR4. Special-category data (health, biometrics, religion, politics, sexuality, trade
  union membership) is flagged as such in the inventory, or its absence is asserted. (P17)
- PR5. Free-text fields that predictably attract personal data (support messages, notes,
  feedback) are treated as personal data in retention and export, not exempted because
  the schema didn't intend it. (P1)

## Lawful basis and consent

- PR6 ★. Each processing purpose names its lawful basis in the inventory, chosen before
  implementation. (P5, P8)
- PR7 ★. Where consent is the basis, the record stores what was consented to, the version
  of the wording shown, the timestamp, and the method — not a boolean. (P5)
- PR8 ★. Consent controls are unticked by default, granular per purpose, and reject is no
  harder to reach than accept — same depth, same prominence. (P6)
- PR9 ★. Withdrawing consent stops the processing, not only the flag: downstream jobs,
  exports, and third-party sends check the current state. (P7)
- PR10. Non-essential cookies and equivalent client-side storage are not set before
  consent; essential ones are enumerated and justified. (P6)
- PR11. Analytics, session recording, and A/B tooling load only after the relevant consent
  and are absent from the initial bundle otherwise. (P6, P10)
- PR12. Marketing communication has its own consent, separate from account and
  transactional messaging, with an unsubscribe that works without login.

## Minimization and design defaults

- PR13 ★. Personal data not required by a stated purpose is not stored — the field is
  absent from the schema, not merely unread. (P9)
- PR14 ★. Analytics and telemetry identify sessions or pseudonymous subjects, not named
  users, unless a stated purpose requires the join. (P10)
- PR15 ★. Application logs and error reports exclude credentials, tokens, full payloads,
  and personal data beyond a pseudonymous identifier. (P10)
- PR16 ★. The privacy-preserving option is the shipped default: no pre-enabled sharing,
  no public-by-default profiles, no opt-out-only tracking. (P11)
- PR17. Where precision is not needed, precision is not stored — a date rather than a
  timestamp, a region rather than coordinates, an age band rather than a birth date. (P9)
- PR18. Test, staging, and demo environments use synthetic or irreversibly anonymized
  data, never a copy of production personal data. (P3, P9)
- PR19. Data shown to support and admin users is limited to what the role needs, and
  access to personal records is logged. (P9)

## Retention and deletion

- PR20 ★. Every personal-data category has a retention period expressed as an enforced
  mechanism — a scheduled job, a TTL, a partition drop — not only as documentation. (P12)
- PR21 ★. Account deletion removes or irreversibly anonymizes personal data in the primary
  store, and the code path that does so enumerates every downstream destination from the
  inventory. (P14)
- PR22 ★. Backup retention is bounded and stated, and the restore procedure documents how
  a deletion request that predates a restore is re-applied. (P12, P14)
- PR23. Logs and analytics have their own retention windows, enforced by configuration
  rather than by nobody looking. (P12)
- PR24. Soft-deleted records are hard-deleted or anonymized on a schedule; a
  `deleted_at` column is not deletion. (P12)
- PR25. Third-party systems holding exported personal data (CRM, email, support,
  warehouse) are covered by the deletion path or listed as a known gap with an owner. (P14)

## Subject rights

- PR26 ★. Access and portability produce the subject's data in a structured, machine-
  readable format, generated by code rather than assembled by hand. (P13)
- PR27 ★. Erasure, rectification, and objection each have an implemented path with a
  stated turnaround, and the identity of the requester is verified before acting. (P13)
- PR28. Subject-rights requests are logged with timestamps, so the response window is
  measurable rather than remembered. (P13)
- PR29. Where a request is refused or partially fulfilled, the reason is recorded and
  communicated. (P13)
- PR30. Automated decisions with significant effects on a person are identified, and a
  human-review path exists. (P17)

## Processors and transfers

- PR31 ★. Every third party receiving personal data is listed with what it receives, why,
  and where it processes — including AI and LLM APIs, which are processors like any
  other. (P15)
- PR32 ★. Personal data is not sent to a service added for convenience without passing
  the same review as any other processor. A new SDK in the bundle is a processor
  decision. (P15)
- PR33. The hosting region for personal data is a deliberate choice recorded in
  infrastructure configuration, not a default accepted at project creation. (P15)
- PR34. Sub-processor changes by a vendor are monitored, since they are inside the
  boundary the user was told about. (P15)
- PR35. Data sent to a processor is the minimum that processor needs, not the full record
  because the API accepted it. (P9, P15)

## Incidents and high-risk processing

- PR36 ★. A breach runbook exists before launch: who is notified, how severity is
  assessed, what the notification deadline is, and who decides. (P16)
- PR37 ★. Detection exists for the events a breach would produce — anomalous bulk reads,
  export spikes, credential stuffing, access to records outside a role's normal
  pattern. (P16)
- PR38. High-risk processing (large-scale profiling, systematic monitoring, special
  categories at scale, automated decisions with legal effect) triggers a written
  assessment before the build starts. (P17)
- PR39. The assessment names the risk to the person, not only the risk to the company,
  and states what would make the processing unacceptable. (P17)

## Interface and disclosure

- PR40 ★. The privacy notice describes what the system actually does, verified against the
  inventory at each release rather than written once. (P2, P4)
- PR41. Data collection that would surprise a reasonable user is surfaced in context, at
  the moment it happens, not only in the notice. (P18)
- PR42. Consent and privacy controls are reachable, operable by keyboard, and labeled
  meaningfully — a dark-patterned or inaccessible consent dialog fails both this pack and
  [ux/wcag](../../ux/wcag/README.md). (P6)
- PR43. Copy explaining a privacy choice states the consequence of each option plainly;
  see [content/ux-writing](../../content/ux-writing/README.md). (P18)

## Supabase and Postgres mapping

Rules for the default stack. They do not replace the ones above — they say where the
platform helps and where it silently does not.

- PR44 ★. Row-level security is enabled on every table holding personal data at creation
  time, not added later. An unprotected table with the anon key exposed is a disclosure
  path, not a to-do. (P4)
- PR45 ★. The project region is chosen deliberately for where personal data may
  reside. (P15)
- PR46. Deletion is implemented as a transaction or a documented cascade that covers
  child tables, storage objects, and auth records — orphaned rows in storage are the
  common miss. (P14, PR21)
- PR47. Retention jobs run as scheduled database jobs or equivalent scheduled functions,
  and a test asserts that data past its window is actually gone. (P12, PR20)
- PR48. Postgres access to personal-data tables is granted per role with column-level
  restriction where a role needs only part of a row. (P9, PR19)
- PR49. Point-in-time recovery windows are set consciously, since they define the real
  floor on how quickly deletion takes effect. (P12, PR22)
